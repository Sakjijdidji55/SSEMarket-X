# 软工集市 Flutter 原生化升级方案

> 版本：v1.0  
> 日期：2026-11-17  
> 适用范围：`ssemarket-x`（Flutter App）中目前仍由 Vue 小程序/WebView 承载的功能  
> 结论先行：**需要改的是约 18–22 个独立页面，不是整个项目重写；建议分 4 期做，优先小说和音乐视频，排行榜/课程可以继续留在 Vue。**

---

## 0. 先说明“升级为 Flutter”到底指什么

这里说的“原生化”，不是把 App 改成 Kotlin/Swift/ArkTS 各写一套平台原生代码，而是：

> **把现在用 Vue 写的小程序页面，改成 Flutter 自己绘制的页面，不再依赖 WebView（网页容器，简单说就是 App 里内置的一个浏览器）。**

Flutter 本身是跨平台框架，界面由 Flutter 引擎直接绘制，不经过浏览器 DOM（网页元素树）。它和“平台原生”有区别：

| 说法 | 实际含义 | 本项目是否采用 |
|---|---|---|
| Flutter 原生渲染 | Dart 写界面，Flutter 引擎绘制，一套代码跑多端 | 是，当前主 App |
| 平台原生 | Android 用 Kotlin、iOS 用 Swift、鸿蒙用 ArkTS 各写一套 | 否，不建议 |
| WebView / H5 | App 里放一个浏览器，加载 Vue 页面 | 仅小程序和少数 H5 页面 |
| Vue 主站 | 浏览器直接访问的网站 | 保留，不改成 Flutter |

所以本文的“升级”= **Vue 小程序页面 → Flutter 页面**；Go 后端、Vue 主站、开发者后台都不动。

## 1. 结论摘要

### 1.1 需要升级的页面数量

| 模块 | 现在是什么 | 需要改的页面 | 优先级 | 预计工作量 |
|---|---|---:|---|---:|
| 小说 | Vue 小程序 | 5 个主页面 | P0 | 2–3 周 |
| 音乐视频 + AI 配音/翻唱 | Vue 小程序 | 4–5 个主页面 | P0 | 2–3 周 |
| 简历 | Vue 小程序 | 4 个主页面 | P1 | 1–2 周 |
| 排行榜 | Vue 小程序 | 1–2 个页面 | P2 | 3–5 天 |
| 课程专区 | Vue 小程序 | 1–2 个页面 | P2 | 3–5 天 |
| 商城小程序 | Vue 小程序，但 App 已有原生商城 | 0（建议下线重复入口） | — | 1–2 天清理 |
| 年度报告、隐私政策、SSO 结果页等 | WebView | 3–5 个可选页面 | P3 | 3–5 天 |
| **合计** | — | **约 18–22 个页面** | — | **6–9 周** |

> 说明：如果把弹窗、空状态、编辑态、Tab 都拆成“界面”来算，会到 30+ 个组件；按用户能感知的“页面”算是 18–22 个。

### 1.2 推荐顺序

1. **先做公共底座**：设计 token、组件库、API 层、缓存、媒体服务；
2. **再做音乐视频**：收益最直接，用户感知最强；
3. **再做小说**：工作量最大，但阅读器/写作最需要原生体验；
4. **最后做简历、排行榜、课程**：低频页面，收益相对小；
5. **商城小程序直接下线**，避免和原生商城重复维护。

## 3. 逐项升级方案

## 3.1 小说模块（P0，5 个页面）

### 3.1.1 小说发现/书架页

**现在做什么**

- 「发现」和「我的书架」两个 Tab；
- 分类筛选、搜索、分页加载；
- 小说卡片：封面、标题、作者、状态、字数、评分等。

**为什么升级**

- 列表是高频入口，Vue 小程序每次打开要重新加载 JS/CSS，首屏比 Flutter 慢；
- 书架需要本地缓存（离线也能看到自己收藏的书），WebView 的本地存储不稳定；
- 原生列表可以更顺滑地做图片懒加载、骨架屏、下拉刷新。

**怎样升级**

1. 新建 `lib/views/novel/novel_home_page.dart`；
2. 用 `ListView.builder` + `RefreshIndicator` 做列表；
3. 分类和搜索复用现有原生筛选组件；
4. `NovelRepository` 封装 `/auth/novel/list`、`/auth/novel/mine`、`/auth/novel/shelf/list`；
5. 书架数据先读本地缓存，再后台刷新；
6. 封面用 `CachedImage`（已有组件），没有封面时显示统一占位图。

**升级后的好处**

- 打开更快，滚动更稳；
- 书架离线可见；
- 和 App 其他页面的字体、间距、颜色统一。

**验收标准**

- 发现/书架切换不白屏；
- 分页到底有“加载更多”；
- 断网时书架能显示上次缓存；
- 封面加载失败有占位图。

---

### 3.1.2 小说详情页

**现在做什么**

- 小说信息、封面、作者、简介；
- 章节列表、分页/加载更多；
- 评分、评论、点赞、删除评论；
- 加入/移出书架；
- 作者可以上传封面、删除小说。

**为什么升级**

- 章节列表和评论是两个长列表，WebView 里容易出现滚动卡顿；
- 上传封面需要相册权限和图片压缩，原生更可靠；
- 评分、收藏、评论都需要即时反馈，原生交互更跟手。

**怎样升级**

1. 新建 `novel_detail_page.dart`；
2. 顶部用 `SliverAppBar` 做封面折叠效果；
3. 章节列表用分页加载，记住滚动位置；
4. 评论区用原生列表 + 输入框，复用帖子评论组件；
5. 封面选择用 `image_picker`，上传前压缩；
6. 收藏、评分、删除操作加乐观更新（先改 UI，失败再回滚）。

**升级后的好处**

- 长列表不卡；
- 封面/评论操作更可靠；
- 和帖子详情页的交互一致。

### 3.1.3 小说阅读器（最复杂，优先级最高）

**现在做什么**

- 章节正文、目录、上一章/下一章；
- 字号、行宽、主题（日间/夜间/护眼等）；
- 阅读进度上报、阅读时长心跳；
- 长按选中文字、复制、划线/段落评论；
- 段落级互动。

**为什么必须升级**

- 阅读器是用户停留最久的页面，WebView 的滚动、选中、长按菜单在 Android/iOS/鸿蒙上表现不一致；
- 长章节 DOM 节点多，滚动容易掉帧；
- 阅读进度、字号、主题需要本地持久化，离线也要能继续读；
- 原生可以做更精确的进度、预加载下一章、后台恢复。

**怎样升级**

1. 新建 `novel_reader_page.dart`；
2. 正文按段落拆分，用 `ListView.builder` 或 `ScrollablePositionedList` 渲染，避免一次创建几千个文本节点；
3. 文字选中：
   - 简单方案：`SelectionArea`（Flutter 自带的选择区域，支持跨组件选中）；
   - 复杂方案：自定义 `SelectableRegion` + `contextMenuBuilder`（自定义长按菜单）；
4. 目录用底部弹层或独立页面；
5. 设置面板：字号、行距、主题、背景色，存 `SharedPreferences`（轻量本地键值存储）；
6. 阅读进度：
   - 本地先存 `novelID + chapterID + 偏移量`；
   - 进入页面先恢复，再后台拉最新章节；
   - 定时上报，退出时强制 flush（立即写入，不等待）；
7. 段落评论：给每个段落挂 `GlobalKey`，点击后滚动到对应位置并弹出评论面板；
8. 预加载下一章，弱网时显示骨架屏，不白屏。

**升级后的好处**

- 滚动顺滑，长章节不卡；
- 字号/主题/进度跨设备更稳定；
- 离线可继续读；
- 长按菜单、复制、段落评论体验统一；
- 可以后台预加载，翻页更快。

**风险**

- 跨段落选中和自定义菜单是 Flutter 的难点，需要单独做技术验证（POC，概念验证：先做一个小样验证可行）；
- 不同平台的长按手势不同，需要真机测试；
- 如果坚持“像素级和网页一样”，排版会受字体和行高影响，需要统一字体资源。

**验收标准**

- 1 万字章节滚动 60fps；
- 退出再进恢复上次位置；
- 字号/主题重启后保留；
- 断网能读已缓存章节；
- Android/iOS/鸿蒙长按菜单都能用。

### 3.1.4 小说写作页

**现在做什么**

- 新建小说、选择已有小说；
- 写章节标题和正文；
- 插入图片段落；
- 上传封面；
- 本地草稿自动保存；
- 提交创建/更新。

**为什么升级**

- 写作是长时间输入，WebView 的键盘避让、输入法兼容、长文本性能都不如原生；
- 草稿需要可靠保存在本地，防止 App 被杀丢失；
- 图片选择和上传需要原生文件/相册能力；
- 自动保存要跟 App 生命周期绑定。

**怎样升级**

1. 新建 `novel_write_page.dart`；
2. 正文编辑器二选一：
   - 纯文本小说：`TextField` + 段落模型，简单可靠；
   - 富文本小说：`flutter_quill`（Flutter 的富文本编辑器），支持加粗/图片；
3. 草稿存本地数据库（推荐 `drift`/`sqflite`，本地 SQL 数据库），每 2–3 秒防抖保存；
4. `AppLifecycleState.paused/inactive` 时强制保存；
5. 图片选择用 `image_picker`，上传前压缩；
6. 封面复用图片上传组件；
7. 提交时做字数、标题、章节校验。

**升级后的好处**

- 输入不卡，键盘不遮挡；
- 草稿不怕丢；
- 图片上传更稳；
- 可以离线写作，联网再提交。

## 3.2 音乐视频 + AI 配音/翻唱（P0，4–5 个页面）

### 3.2.1 音乐视频首页（Media Hub）

**现在做什么**

- 音乐库、AI 配音、AI 翻唱、视频四个入口；
- 最近音乐、AI 翻唱作品；
- 播放音乐/翻唱。

**为什么升级**

- 这是媒体功能的门户，原生页面可以统一播放器状态；
- WebView 里的音频和主 App 播放器会互相抢音频焦点（谁在占用扬声器）；
- 原生可以做到“退出页面继续播放”。

**怎样升级**

1. 新建 `media_hub_page.dart`；
2. 复用 `MusicPlayerService`（已有原生播放服务）；
3. 四个入口用原生卡片；
4. 最近音乐/翻唱列表用原生列表；
5. 点击播放后显示全局迷你播放条（已有 `music_mini_bar.dart`）。

**升级后的好处**

- 媒体入口和播放器一体化；
- 不会和 WebView 音频打架；
- 播放状态全局可见。

### 3.2.2 音乐库

**现在做什么**

- 搜索、分页、播放全部；
- 上传音乐（音频 + 封面）；
- 删除自己的音乐；
- 播放/暂停/上一首/下一首。

**为什么升级**

- 音乐是典型的需要后台播放的功能；
- WebView 的 `<audio>` 在锁屏、切后台、蓝牙耳机、来电打断时行为不可控；
- 原生可以接系统媒体通知、锁屏控制、音频焦点。

**怎样升级**

1. 复用已有 `MusicPlayerService` 和 `just_audio`；
2. 接 `audio_service`（把播放器接入系统媒体控制：通知栏、锁屏、耳机按键）；
3. Android 前台服务（系统要求后台播放时显示常驻通知）；
4. iOS 配置 `UIBackgroundModes: audio`；
5. 上传用 `file_picker` + `image_picker`，先读时长再提交；
6. 列表分页、搜索、删除复用原生组件。

**升级后的好处**

- 锁屏/通知栏可控；
- 切后台不断音；
- 蓝牙耳机、来电打断处理更好；
- 上传更稳定。

**平台注意**

- Windows 目前 `just_audio` 支持不完整，需要单独评估（可保留 Edge 窗口作为 Windows 兜底）；
- 鸿蒙需要平台通道（MethodChannel，Flutter 和原生代码之间的桥）接系统媒体能力。

### 3.2.3 AI 配音（TTS）

**现在做什么**

- 选择音色、试听；
- 输入文字、调整语速；
- 提交异步任务、轮询进度；
- 播放/下载 WAV。

**为什么升级**

- TTS 是异步任务，可能几十秒到几分钟，原生可以更好地做后台轮询和通知；
- 音频结果需要下载/分享，原生文件能力更可靠；
- 避免用户切后台后 WebView 定时器被系统暂停，导致进度不动。

**怎样升级**

1. 新建 `tts_page.dart`；
2. 音色列表、文本输入、语速滑杆；
3. 提交后返回 `taskId`，用带退避的轮询（不是死循环）；
4. App 切后台时暂停轮询，回前台恢复；
5. 完成后下载到本地缓存，支持播放/分享/保存；
6. TTS API Key 只放在 mp-service 服务端，App 只调 `/v1/tts/*` 代理，绝不能把 Key 打进 App。

**升级后的好处**

- 长任务不中断；
- 进度和结果更可靠；
- 音频可离线播放；
- 密钥不落到客户端。

### 3.2.4 AI 翻唱

**现在做什么**

- 选音色、选歌曲（显示歌手和 mm:ss 时长）；
- 提交翻唱任务；
- 轮询进度；
- 试听/下载成品；
- 我的翻唱列表。

**为什么升级**

- 翻唱任务时间更长，原生后台任务和通知更合适；
- 歌曲列表、试听、下载都是媒体操作，原生体验更统一；
- 可以复用音乐播放器的缓存和通知。

**怎样升级**

1. 新建 `cover_page.dart`；
2. 歌曲列表复用 3.1 的原生列表样式；
3. 任务提交后保存 `coverId`，用轮询 + 本地通知提醒完成；
4. 成品下载到缓存，播放用 `just_audio`；
5. 我的翻唱列表显示时长、音色、日期；
6. 失败任务给出明确原因和重试。

**升级后的好处**

- 生成完成能通知用户；
- 切后台不丢任务；
- 试听/下载更顺；
- 和音乐库共用播放器。

### 3.2.5 视频列表/详情

**现在做什么**

- 视频列表、搜索、分页；
- 视频详情、播放、记录播放量。

**为什么升级**

- 视频播放对性能、全屏、横屏、音频焦点要求高；
- WebView 播放器在部分机型上全屏/手势冲突；
- 原生可以接系统画中画（PiP，Picture-in-Picture：小窗播放）、后台音频。

**怎样升级**

1. 列表页用原生网格/列表；
2. 详情页用 `video_player` 或 `media_kit`；
3. 全屏、横屏、手势调节音量/亮度；
4. 播放进度上报；
5. 可选画中画（Android/iOS 支持情况不同）。

**升级后的好处**

- 播放更稳；
- 全屏/横屏体验更好；
- 可扩展画中画和后台播放。

## 3.3 简历模块（P1，4 个页面）

### 3.3.1 简历列表/我的简历

**现在做什么**

- 公开简历列表、我的简历；
- 搜索、分页；
- 上传入口、详情入口。

**为什么升级**

- 简历是低频但重要的工具，原生表单和文件能力更可靠；
- 列表可以离线缓存，打开更快；
- 和 App 的分享/下载体系统一。

**怎样升级**

1. 新建 `resume_list_page.dart`；
2. 两个 Tab：公开/我的；
3. 分页列表、搜索、空状态；
4. 上传按钮进入原生上传页。

---

### 3.3.2 简历上传

**现在做什么**

- 选择 PDF/图片；
- 校验文件类型和大小；
- 上传、填写标题/标签；
- 返回列表。

**为什么升级**

- WebView 的 `<input type=file>` 在 Android/iOS/鸿蒙上行为不一致；
- 原生文件选择器可以直接访问“文件”App、相册、云盘；
- 上传进度和失败重试更可控。

**怎样升级**

1. 用 `file_picker` 选择 PDF/DOC/图片；
2. 用 `path_provider` 复制到临时目录；
3. 用 `dio` 或 `http` 做 multipart 上传，显示进度；
4. 校验大小/类型；
5. 上传成功后刷新列表。

---

### 3.3.3 简历详情/编辑

**现在做什么**

- 查看简历信息；
- 编辑标题/描述/标签；
- 预览 PDF/图片；
- 下载、分享、删除。

**为什么升级**

- PDF 预览在 WebView 里依赖浏览器 PDF 插件，移动端经常打不开；
- 原生可以用 `pdfx`/`pdf_render` 渲染 PDF 页面；
- 下载/分享走系统能力，文件能在“文件”App 里找到。

**怎样升级**

1. 详情页用原生布局；
2. PDF 用 `pdfx` 渲染缩略图/分页；
3. 图片简历用原生图片查看器（已有 `ImageViewer`）；
4. 下载到 App 文档目录或系统下载目录；
5. 分享用 `share_plus`；
6. 删除前二次确认。

**升级后的好处**

- PDF 不再打不开；
- 下载/分享路径清楚；
- 编辑保存更可靠。

## 3.6 商城小程序：不建议升级，建议下线重复入口

**现状**

- 少维护一套；
- 用户路径更短；
- 避免“原生商城”和“小程序商城”两个入口打架。

## 4. 升级前必须做的公共底座

如果直接一页一页写，最后会出现“每页样式不一样、API 各写一套”的问题。建议先做下面这些。

### 4.1 设计 token（设计变量）

“token”在这里不是登录凭证，而是**颜色、字号、间距、圆角、阴影的统一定义**。

从 Vue 的 CSS 里抽出一份：

```text
颜色：主色、强调色、背景、卡片、边框、文字一级/二级/三级
字号：10.5 / 11.5 / 12.5 / 13.5 / 15 / 20 / 28
间距：4 / 8 / 10 / 12 / 14 / 16 / 20
圆角：8 / 10 / 12 / 16 / 20
阴影：卡片、浮层、弹窗
```

Flutter 用 `ThemeExtension`（主题扩展）统一管理，页面里不要写死颜色和字号。

### 4.2 组件库

把 Vue 常用组件在 Flutter 里做一套对应实现：

- 按钮：主按钮、次按钮、文字按钮、危险按钮；
- 输入框：单行、多行、密码、搜索；
- 卡片：帖子卡、用户卡、音乐卡、简历卡；
- 列表：加载中、空状态、错误重试、加载更多；
- 弹窗：确认框、底部弹层、ActionSheet；
- 标签/徽章/骨架屏。

这样升级页面时是“拼组件”，不是每页重新画。

### 4.3 API 层

- 统一 `ApiClient`：base URL、超时、重试、错误码、登录过期；
- 统一 token 刷新：401 时只刷新一次，避免并发刷新；
- 统一错误提示：网络错误、业务错误、权限错误；
- 统一分页模型：`offset/limit`、`hasMore`、`total`；
- 为小程序/主站/App 保持同一套接口契约。

### 4.4 本地存储

| 数据 | 方案 |
|---|---|
| 阅读进度、字号、主题、播放进度 | `SharedPreferences`（轻量键值） |
| 小说章节缓存、简历文件、任务记录 | `drift`/`sqflite`（本地 SQL 数据库） |
| 图片/音频缓存 | 文件目录 + 缓存索引 |
| 登录 token（敏感） | `flutter_secure_storage`（系统安全存储） |

### 4.5 媒体与系统能力

- 音频：`just_audio` + `audio_service`；
- 视频：`video_player` 或 `media_kit`；
- 文件：`file_picker`；
- 图片：`image_picker`；
- PDF：`pdfx`；
- 分享：`share_plus`；
- 通知：`flutter_local_notifications` + 鸿蒙平台通道；
- 后台：Android 前台服务、iOS 音频后台模式。

### 4.6 功能开关（Feature Flag）

“功能开关”= 一个远程配置，可以决定用户走原生页还是旧 Vue 页。

```text
novel_native = true/false
media_native = true/false
resume_native = true/false
```

好处：

- 新页面出问题可以一键切回旧页面；
- 可以按用户/设备灰度；
- 不用发新版就能关闭问题功能。

### 4.7 测试

- 单元测试：API 解析、分页、进度计算；
- Widget 测试：列表、表单、空状态；
- Golden 测试：把页面渲染成图片和设计稿对比（视觉回归）；
- 集成测试：登录 → 阅读 → 退出 → 恢复进度；
- 真机测试：Android/iOS/鸿蒙/Windows。

### 4.8 监控

- 崩溃收集；
- 页面加载耗时；
- API 失败率；
- 播放失败率；
- 阅读器滚动帧率。

## 6. 为什么不建议一次性全改

推荐用“绞杀者模式”（Strangler Pattern：新功能一点点替换旧功能，旧功能先保留，等新功能稳定再拆掉）。

做法：

1. 旧 Vue 页面先不删；
2. 新 Flutter 页面用功能开关控制；
3. 灰度 5% → 20% → 50% → 100%；
4. 对比两边的 API 结果、错误率、用户反馈；
5. 稳定后再删除旧入口。

好处：

- 出问题能立刻回退；
- 不用一个版本承担所有风险；
- 可以按模块逐步验收。

## 7. 怎样做到和 Vue 样式“尽量一模一样”

### 7.1 可以完全一致的部分

- 颜色、字号、间距、圆角、阴影；
- 卡片结构、列表行高、图标大小；
- 按钮/输入框/标签/空状态；
- 页面信息层级和交互流程。

### 7.2 很难 100% 一致的部分

| Web 能力 | Flutter 情况 | 处理方式 |
|---|---|---|
| CSS `backdrop-filter` 毛玻璃 | 需要 `BackdropFilter`，性能成本不同 | 降低模糊半径或改用半透明色 |
| CSS 复杂动画 | 需要 `AnimationController` 重写 | 保留关键动画，简化次要动画 |
| 浏览器字体 | 各平台字体不同 | 内置统一字体或接受平台差异 |
| Markdown/KaTeX 公式 | Flutter 渲染器不同 | 用 `flutter_math_fork` 等库，复杂公式单独测试 |
| 文本选中/长按菜单 | 平台行为不同 | 自定义 `contextMenuBuilder` |
| 响应式 PC 布局 | Flutter 要自己写断点 | 用 `LayoutBuilder` 做手机/平板/桌面三档 |

### 7.3 推荐验收方式

1. 每个页面准备 Vue 截图（手机/桌面各一张）；
2. Flutter 同尺寸截图；
3. 用 golden test（截图对比测试）做像素差异检查；
4. 允许 2–5% 差异（字体/抗锯齿），超过就修；
5. 真机再走一遍。

**现实目标**：90%–95% 视觉一致，用户看不出明显区别；追求 100% 像素一致会陷入无底洞。

## 9. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 阅读器选中/长按复杂 | Flutter 跨段落选中不如浏览器成熟 | 先做 POC（小样验证），不行就退化为“按段落选择” |
| 后台播放平台差异 | Android/iOS/鸿蒙/Windows 行为不同 | 做平台矩阵，Windows 可保留 Edge 兜底 |
| TTS/翻唱任务长 | 轮询可能几分钟 | 后台任务 + 本地通知 + 回前台恢复 |
| PDF 预览 | 不同 PDF 字体/扫描件渲染差异 | 用成熟 `pdfx`，准备图片兜底 |
| 样式不一致 | Flutter 和 CSS 渲染不同 | design token + golden test + 逐页验收 |
| 两套代码并行 | 迁移期维护成本高 | 功能开关 + 明确下线时间 |
| 安装包变大 | 新增媒体/PDF 库 | 按需加载、拆分 ABI、移除无用依赖 |

## 12. 术语表（高级词翻译成大白话）

| 术语 | 大白话 |
|---|---|
| Flutter | 一套代码画多端界面的框架，界面由它自己绘制 |
| Dart | Flutter 使用的编程语言 |
| WebView | App 里内置的浏览器，用来加载网页 |
| Vue | 写网页的前端框架 |
| 原生渲染 | 不经过浏览器，直接由系统/引擎画界面 |
| 平台原生 | Android 用 Kotlin、iOS 用 Swift、鸿蒙用 ArkTS 各写一套 |
| Token（设计 token） | 颜色、字号、间距等设计变量的统一定义 |
| Token（登录 token） | 登录后拿到的凭证，证明“你是谁” |
| API | 前后端约定好的接口，App 按格式请求数据 |
| Route（路由） | 页面地址和页面之间的跳转规则 |
| Repository | 数据仓库层，把 API、缓存、数据库包在一起 |
| 状态管理 | 页面数据怎么保存、怎么通知界面刷新 |
| 本地数据库 | 存在手机里的数据库，断网也能读 |
| SharedPreferences | 手机里的轻量键值存储，适合存设置 |
| Secure Storage | 系统加密存储，适合存登录凭证 |
| 前台服务 | Android 的后台常驻服务，播放音乐/下载时显示通知 |
| 音频焦点 | 谁有权使用扬声器，打电话/放视频时会互相抢占 |
| TTS | Text To Speech，文字转语音 |
| RVC | 一种 AI 音色转换/翻唱技术 |
| 轮询 | 每隔几秒问一次服务器“任务完成了吗” |
| 退避 | 失败后不要立刻狂重试，间隔逐渐拉长 |
| Feature Flag | 功能开关，远程控制某功能开/关 |
| 灰度 | 先让一小部分用户用新功能，没问题再扩大 |
| Strangler Pattern | 绞杀者模式：新功能逐步替换旧功能，旧的先保留兜底 |
| Golden Test | 把页面截图和设计稿对比的自动测试 |
| POC | 概念验证，先做一个小样证明技术可行 |
| PiP | Picture-in-Picture，画中画小窗播放 |
| PDF | 便携文档格式，简历常用 |
| Multipart | 一种上传文件的 HTTP 请求格式 |

---

## 13. 最终建议

### 最值得做的

1. **小说阅读器 + 写作**：体验提升最大，用户停留时间最长；
2. **音乐播放器 + TTS/翻唱**：后台播放、通知、任务可靠性收益明显；
3. **简历 PDF 预览/上传**：WebView 最容易出问题的地方。

### 可以缓一缓的

- 排行榜、课程专区：页面简单，Vue 小程序已经够用；
- 年度报告、隐私政策、SSO 结果页：低频，继续 WebView 更划算。

### 不建议做的

- 把整个 Vue 主站搬进 Flutter；
- 为了“纯原生”用 Kotlin/Swift/ArkTS 重写三套；
- 把商城小程序再原生写一遍（App 已有原生商城）。

### 一句话

> **先把“高频、重交互、需要系统能力”的 9–10 个核心页面原生化，剩下的低频页面继续用 Vue 小程序。这样投入产出比最高，也不会把项目拖进 3–4 倍工作量的深坑。**
